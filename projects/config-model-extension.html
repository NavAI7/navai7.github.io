Config Model Extension

Problem

Configuration carries a high interaction cost: multiple clicks and complex setups, especially for backend entities like plugins and procedures. It demands a steep cognitive load, a deep, tribal understanding of the existing configuration before a single change is safe to make. And it depends on fragile, manual dependency tracking, where getting the creation order wrong introduces errors that slow delivery down further, turning a 4–6 month implementation into a slow, expert-bound slog.

Scope, precisely

This is the o9 Solution Architect agent itself, plus the Create/Read/Update tools, skills, and configuration-modeling best practices built specifically to power it. The tools weren't built as a generic platform API first and handed to an agent second, they were shaped by what this agent needed in order to act safely.

Users

The user is the configurator, an implementation consultant who today builds or extends a tenant by hand, either from a precise spec or from a vague business ask they have to translate into config themselves. They interact directly with the o9 Solution Architect agent to do that work; the agent's own needs, structured errors, predictable ordering, resumable phases, shaped its underlying tools as much as any configurator's did.

Why existing approaches failed

Agentic frameworks could already reason about plans and sequencing well before this existed. What they lacked was a reliable, complete, machine-consumable interface to the platform's own configuration entities. Without first-class CRUD tools, agents couldn't act at all, no matter how capable the underlying model was. Any partial automation attempt was forced to screen-scrape the UI or call internal APIs that were never designed for programmatic consumers, and every one of those attempts had to reinvent its own safety net for validation, ordering, and rollback, or skip it entirely and hope nothing broke.

Product insight

The bottleneck was never agent intelligence, it was the absence of a trustworthy interface for that intelligence to act through. That reframing changed the whole scope of this initiative: instead of building a smarter agent on top of whatever existed, the job was to build the agent and the tooling foundation beneath it together, with the platform itself enforcing the safety the agent shouldn't be trusted to enforce on its own.

System approach

Architecture — grounded in two graphs, the agent proposes a phased plan; each phase clears human approval and dependency-ordered CRUD tooling before it lands on the platform, with out-of-order calls rejected back to the agent instead of leaving a partial state.

Dependency-ordered tooling

The tooling layer enforces one non-negotiable rule: entities must be created in the order the platform actually depends on them.

Dimensions → Attributes → Attribute Properties → Hierarchies → Plans → Measure Groups → Measures → Named Sets → Procedures / Active Rules → Plugins

Enforcement is the tool's job, not the agent's: a call against an entity whose upstream dependencies don't exist yet gets rejected with a descriptive, actionable error instead of being allowed to leave a partially valid state behind.

Two capabilities, one agent

Greenfield provisioning

Stand up a new tenant's entire ontology and computation layer from scratch: structure first, then data-bearing entities, then rules, then plugins last.

Extending an existing solution

Grow an already-configured tenant without starting over, for example moving it from a basic statistical forecasting engine to a driver-based ML forecast engine, which means extending the ontology (dimensions, measures) and building the new computation layer underneath it.

Either way, the o9 Solution Architect grounds itself in two graphs before proposing anything: the tenant's own Config Graph, and a separate, cross-tenant Reference Model Graph of standardized solution patterns. Depending on the ask, it either executes directly against a known spec or proposes a phased plan, structure first, then data-bearing entities, then rules, then plugins last, submitted for review one phase at a time before anything runs.

Key PM decisions

  • Built the tools as the agent's foundation, not a generic API. Structured errors, predictable ordering, resumable phases, and modeling best practices were designed in because the o9 Solution Architect needed them, not bolted on afterward for a hypothetical external caller.
  • Scoped exactly which edits the agent could make safely on its own. Not every config entity tolerates the same blast radius of change, so some, like renaming an entity that's already referenced by procedures or plugins elsewhere, keep the same limitation the manual UI has today rather than ship a new, only-partial safety guarantee that looks safer than it is.
  • Decided against a dedicated UI up front. Shipping the agent's core capabilities first meant real usage patterns existed before deciding what a configuration UI should even look like. That later became Config Designer UI.
  • Chose deliberately boring success metrics. Tool coverage, call success rate, and dependency-rejection rate, not agent reasoning quality. A foundational layer earns trust by being measurable, not by being clever.

Human-in-the-loop & trust

No phase of a proposed plan executes unattended. The configurator can accept, edit, or reject each phase before the agent proceeds to the tool calls for it, human-in-the-loop by design, not as an afterthought bolted onto an autonomous system.

Failure handling gets the same treatment as a first-class flow, not an edge case. When a tool call fails, validation error, platform error, or dependency violation, the agent halts the sequence and rolls back to the last stable state, then returns a structured error: the failing entity, the failure reason, the rollback outcome, and, where determinable, a remediation hint. The agent surfaces that to the configurator in plain language and re-proposes the affected phase, instead of silently continuing or aborting the entire plan. Update tools are also required to surface downstream dependents before applying a change, so a configurator approving a risky update is making an informed call, not a blind one.

Tradeoffs & risks

The sharpest risk is that modifying an upstream entity, a dimension, say, can silently break a downstream measure or active rule already running in production. Surfacing dependents before a change reduces that risk but doesn't eliminate it, since a human still has to read and act on what's surfaced. A second, messier problem: some entity creation still requires a tenant restart before downstream entities can be created, and today's errors aren't always descriptive enough for an agent to recover from on its own. Rather than guess at a fix, that was flagged explicitly as an open design question for the architecture review, not something worth papering over with a false sense of completeness.

Impact

4–6mo → wks typical build time, greenfield & extension

Implementations that used to take four to six months can ship in weeks, sometimes days, for both greenfield tenant provisioning and extending an existing solution, for example moving a tenant from statistical to ML-based forecasting. The Solution Architect agent built here also became the engine behind Config Designer UI, and a related, adjacent tool surface reuses the same agent to generate synthetic dimension and measure-group data for full proof-of-concept builds.
