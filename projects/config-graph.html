Problem

Agentic AI systems working inside o9 had no native way to understand a tenant's own configuration. An agent had no reliable way to answer the questions an expert implementer answers from memory: what columns a given report actually contains, which measuresThe numeric metrics being tracked, e.g. sales or inventory. feed into a plugin, or which actions a report even supports. Every one of those had to be told to the agent by hand, one prompt at a time, and re-told the moment configuration changed. Every agent product on the roadmap, from a config-building agent to a data-lineage agent, needed the same missing thing underneath it: a real, queryable model of what exists on a tenant and how it connects.

Why it matters

Graph, industry, and platform knowledge combined is what unlocks powerful agent applications on top of o9, from explainability to autonomous config extension.

Users

Config Graph has no end users of its own, it's consumed internally by other products and agents on the platform: Agent Builder (which people use to build new agents), the o9 Solution Architect (which configurators use to extend a tenant), Skill Builder, and Synthetic Data Generation. Each of those needed the same missing thing, a way to ground itself in a tenant's real state, and each was solving that independently before this existed.

The people who actually feel Config Graph, without ever touching it directly, are anyone talking to any agent built on the platform. When someone asks an agent for "sales data," the graph is what disambiguates which of a tenant's dozens of similarly-named measures "sales" actually refers to, instead of the agent guessing.

Why existing approaches failed

Before this, "grounding" an agent in a tenant meant one of three things, and none of them held up past a demo. Hardcoding tenant knowledge into a prompt breaks the moment configuration changes, which is constantly. Retrieving from a flat catalog or a plain vector index finds a similar-sounding name but throws away the relationships between entities, which is exactly what disambiguates one measure from another. And asking the model to just infer structure from names alone works until two measures have almost the same name and completely different meanings, which is the normal case on a real tenant, not the exception.

Product insight

The reframe that mattered: agents don't need more context, they need the same relational mental model a solution architect already carries. A measure isn't a string, it's a node with defined inputs, outputs, and a container it lives in. Platform entities are relational by construction, a pluginA packaged calculation or automation module that runs on the platform. takes measures in and produces a measure out, a view surfaces a set of reports, a report is powered by an action button, so the fix wasn't a better prompt or a bigger retrieval index. It was building the graph that structure already implies.

System approach

Architecture — tenant config is ingested into typed graph nodes and relationships, enriched with derived relationships and LLM-written descriptions, stored in FalkorDB, and exposed through three tools that every downstream agent product consumes.

Modeling the platform

Every config entity, attributes, measure groups, measures, reports, views, plugins, procedures, active rules, and action buttons, is modeled as a graph node with typed, directional relationships between them. If measures A and B feed into a plugin XYZ that outputs measure C, the graph carries an INPUTS_TO relationship from A and B into XYZ, and an OUTPUTS_TO relationship from XYZ into C.

Choosing the database

The graph needed to run natively at scale, 100+ tenants, each with their own graph, on infrastructure the platform team could actually operate, which ruled out anything that only supports multi-tenancy as a paid enterprise feature. Native Cypher support mattered just as much, since LLMs already generate it well.

PlatformMulti-tenancyCypherLicenseVerdict
FalkorDB Chosen Native high-density support: 10k+ graphs per cluster Native OpenCypher SSPLv1 Best balance of tenant density, native AI features, and easy migration. Runs on Redis, which the platform already operates.
Memgraph Enterprise-only Native OpenCypher BSL Fastest engine and an easy migration, but multi-tenancy sits behind a paid enterprise license.
Neo4j Enterprise-only Native, the standard GPLv3 / Commercial Best ecosystem and docs, but running 100+ JVMs on Community Edition isn't viable, and multi-database is Enterprise-only.

The license column carried real legal weight, not just a technical one: SSPL, BSL, and GPL/Commercial terms each expose a platform vendor bundling the database differently, so FalkorDB's license went through legal review before it was chosen, not just an engineering comparison.

Capturing relationships that aren't explicit

Some relationships are already explicit in a tenant's configuration, a measure belongs to a measure group, a view belongs to a workspace. Others aren't stored anywhere as a direct link and have to be derived: which procedure actually computes a given measure, or which report exposes it downstream, has to be traced through code and cross-references rather than read off a single config record. Getting that derived layer right mattered as much as covering more entity types, since it's exactly the relationships an implementer would otherwise trace by hand.

Keeping it grounded and searchable

Ingestion reads a tenant's live configuration directly and is generic across entity types, so onboarding a new tenant's graph doesn't need bespoke engineering per tenant, which is what makes 100+ tenants viable at all. An LLM-written description layer turns a node named Rpt_NPI_Fcst_v3 into something an agent can search by meaning, and three tools sit on top for agents to use together: reading the schema, searching it, and querying it.

Key PM decisions

  • Shipped as pure infrastructure, no UI, on purpose. Getting it adopted by Agent Builder, Skill Builder, and Config Model Extension first meant real usage patterns existed before deciding what a graph-exploration UI should even look like. Config Designer UI came later, informed by that usage — a deliberate sequencing call, not a resourcing gap.
  • Prioritized coverage breadth over exhaustive depth, to fit a realistic timeline. Ten core entity types across every tenant beat perfect metadata on a handful of entity types, since the goal was something usable at 100+ tenant scale from day one, not a showcase on one tenant, and it kept the initial build achievable instead of open-ended. That traded off richer metadata on any single entity type, and a larger database footprint, for a graph every downstream team could rely on immediately.
  • Modeled derived relationships, not just explicit ones. Deciding which implicit relationships, like which procedure actually computes a measure, were worth deriving and encoding was as much a scoping call as picking entity types, since getting it wrong either bloats the graph with low-value inference or leaves gaps agents fall into.
  • Accepted an open infrastructure question rather than blocking on it. FalkorDB's memory cost at full multi-tenant scale couldn't be answered definitively without production load, so the call was to ship on the strongest available evidence and monitor, not stall the whole roadmap waiting for certainty no evaluation could have provided anyway.

Human-in-the-loop & trust

Config Graph never writes back to the platform, it's a derived, read-oriented layer synced from configuration, never authoritative over it. That constrains the trust problem by construction: correctness is enforced upstream, a node only gets created in the graph after its platform counterpart is validated to exist, so any agent consuming the graph inherits that guarantee instead of needing its own verification step.

The one place this needed a deliberate boundary was description generation. LLM-written descriptions are attached to nodes purely as search metadata and never fed back into the platform's own config, keeping a hard line between "context that helps an agent find the right node" and "the actual system of record."

Tradeoffs & risks

  • Breadth over depth means real blind spots. Entity types outside the initial ten aren't modeled yet, so an agent can still hit a gap the graph doesn't cover.
  • Derived relationships can be wrong. Some of the relationships the graph encodes aren't read directly off configuration, they're inferred, and an inference can be incorrect in a way a directly-stored relationship can't be. An agent that trusts a bad inferred edge inherits that mistake silently.
  • FalkorDB's memory footprint at full scale is still the main open risk. It was a knowing bet, not a solved problem, and stays something the team actively watches rather than something closed out at launch.
  • Generated descriptions can be wrong or bland. Since semantic search depends on them, a weak description directly costs search precision. This is mitigated by better grounding context, not eliminated.

Impact

Config Graph is the foundational context layer for Agent Builder and Skill Builder, so any agent can be scoped with real platform context instead of hardcoded knowledge. Config Model Extension and Synthetic Data Generation are both built directly on top of it, which is the direct payoff of prioritizing breadth-first infrastructure over a polished single-tenant demo: four separate product teams could build on the same graph instead of each solving grounding on their own. Beyond that, it's the disambiguation layer behind a huge share of natural-language queries on the platform: when someone asks an agent to "get me sales data," Config Graph is what resolves "sales" to the right measure, and it lets a user ask why a number is what it is and get a real trace back through the procedures and plugins that computed it, instead of a shrug.
