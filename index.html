About

An agent is only as good as what it knows about the company it's working in. My job on o9's AI R&D team is that knowledge: how it's modelled, how agents query it, and what they're allowed to change once they have it.

What I own

Three products that stack. The Config Graph is the ontology of a customer's o9 setup. Config Model Extension is the agent that builds and extends that setup using the graph. Config Designer UI is the workspace that puts the graph and the agent on one page. I also own Usage Analytics, an intelligence layer in the platform that shows how people actually work on it.

How technical

I design the graph schema with engineering, decide what an agent may do without asking, and chose the graph database it runs on. I also built Flo9 on my own and won o9's hackathon with it.

Before product

Three years in delivery at o9, implementing supply chain planning for Fortune 500 retailers. I led the replenishment planning build for Starbucks. Configuration was slow, fragile and locked in a few experts' heads, and I was one of the people doing it. That's the problem I now solve with AI.

Education

B.Tech, Electrical and Electronics Engineering, NIT Karnataka, Surathkal.

02

The knowledge layer

AI can't help run a business it doesn't understand. So I model the enterprise once, as a graph that AI can understand, work on top of and extend.

SOURCE

Platform

A customer's live o9 configuration: dimensions, measures, plugins, procedures, reports and views. It stays the system of record. The graph is derived from it and never writes back.

↓ synced from live config, read-only
LAYER 1

Knowledge layer

The shared context and ontology layer for AI across the platform. It models ten kinds of configuration entity and how they relate, including links no config record stores, like which procedure computes a measure.

  • Config Graph (EKG)
  • Reference Model Graph
One ontology, used across the board Every agentic workflow gets its context here
  • Solution Architect
  • Agent Builder
  • Skill Builder
  • Synthetic Data
  • All other agent workflows
↓ read schema · search · query
LAYER 2

Agents act

Agents plan and execute configuration, and generate test data. The configuration tools enforce dependency order and roll back on failure, so safety doesn't depend on the model behaving.

  • Config Model Extension
  • Synthetic Data Generation
↓ phased plan, sent for approval
LAYER 3

People decide

Implementers browse the tenant as a graph and work with the agent on the same page, reviewing its plan one phase at a time and accepting, editing or rejecting it. Nothing runs unattended.

  • Config Designer UI

Why context matters

For example, someone asks an agent“Get me the sales number from Demand Review.”

Without the graph

The agent searches by name and finds four measures that all look right.

  • Sales
  • Sales_Adj
  • Sales_Net_v2
  • Sales_LY

It has to guess, or ask someone who knows the setup.

With the graph

The agent starts at the report and follows the relationships.

  1. ReportDemand Review
  2. Shows measureSales_Net_v2
  3. Computed byCalc_Net_Sales

It gets the right number, and can show where it came from.

How I work

How I take an AI product from a messy problem to something people trust.

  1. 01

    Start where the work hurts

    I begin with what's slow, fragile or stuck in one expert's head. The model comes second.

  2. 02

    Foundation before interface

    I ship what others can build on, then design the screen around real usage.

  3. 03

    Draw the line for the agent

    I decide what it does alone, where it must ask and how it fails.

  4. 04

    Put safety in the tools

    A prompt asks the model to behave. A tool can refuse.

  5. 05

    Pick boring metrics

    I track whether the job gets done reliably, long before how clever it sounds.

  6. 06

    Let the skeptic check

    People adopt what they can verify, so every answer leads back to its source.
